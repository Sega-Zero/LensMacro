# Lens

Composable lenses for Swift, generated by a macro — "functional getters and
setters", convenient when changing parts of immutable objects. Featuring dot
notation, zero new operators.

The API is based on [lenso](https://github.com/narfdotpl/lenso) by
[Maciej Konieczny](http://narf.pl/posts/lenses-in-swift).

```swift
import Lens

@Lens
struct Address {
    var street: String
}

@Lens
struct Person {
    var name: String
    var address: Address
}
```

```swift
let author = Person(name: "Maciej Konieczny", address: Address(street: "Sesame Street"))

// Read and update through plain lenses
Person.Lenses.name.get(author)              // "Maciej Konieczny"
Person.Lenses.name.set("narf", author)      // Person with name "narf"

// Compose lenses
let personStreetLens = Person.Lenses.address.compose(Address.Lenses.street)
personStreetLens.get(author)                // "Sesame Street"
personStreetLens.set("Wisteria Lane", author)

// Or use bound lenses — dot notation without manual composition
let author2 = author.throughLens.address.street.set("Baker Street")
author.throughLens.name.get()               // "Maciej Konieczny"

// Change several fields at once — omitted fields keep their values
let author3 = author.throughLens.changing(
    name: "narf",
    address: Address(street: "Baker Street")
)
```

## What the macro generates

```swift
@Lens
struct Person {
    var name: String
    var address: Address
}
```

expands to:

```swift
struct Person {
    var name: String
    var address: Address

    enum Lenses {
        static let name: LensType.LensValue<Person, String> = LensType.LensValue(
            get: { $0.name },
            set: { (newValue, whole) in
                var copy = whole
                copy.name = newValue
                return copy
            }
        )
        // ... one entry per stored `var` property
    }

    @dynamicMemberLookup
    struct ThroughLens {
        let instance: Person

        func get() -> Person {
            instance
        }

        func set(_ newValue: Person) -> Person {
            newValue
        }

        subscript<Subpart>(dynamicMember keyPath: WritableKeyPath<Person, Subpart>) -> LensType.BoundLensValue<Person, Subpart> {
            LensType.BoundLensValue(instance: instance, lens: LensType.LensValue(keyPath))
        }

        func changing(name: String? = nil, address: Address? = nil) -> Person {
            self.set(Person(
                name: name ?? self.get().name,
                address: address ?? self.get().address
            ))
        }
    }

    var throughLens: ThroughLens {
        ThroughLens(instance: self)
    }
}
```

Generated references go through the `LensType` namespace — a hygiene detail:
even if your module declares its own types named `Lens` or `BoundLens`, they
can't shadow the ones the generated code needs.

Lenses never mutate their input; `set` returns an updated copy. Note the
lenso argument order: the new part comes first — `set(newPart, whole)`.

## Bound lenses

`BoundLens` is a lens that is already "used half way": it has a `Whole`
instance associated with it, which allows chaining through properties with
dot notation.

- `author.throughLens` — binds the identity lens to `author`
- `.get()` — returns the focused part
- `.set(_:)` — returns a copy of the whole with the part replaced
- `.someProperty` — chains deeper (`BoundLens` uses `@dynamicMemberLookup`
  over writable key paths)
- `.changing(...)` — returns a copy with several fields replaced at once
  (see below)

```swift
team.throughLens.lead.address.street.get()              // read deep
team.throughLens.lead.address.street.set("Baker Street") // update deep
```

Because chains are built from key paths, they can go through `var`
properties of any type — chained types do not need to be annotated with
`@Lens` themselves.

Key paths are not writable for constants, so stored `let` properties get
dedicated bound lenses on the struct's own `throughLens` instead. They
rebuild the value through the memberwise initializer (like `changing`), so
they work exactly like `var` chains:

```swift
@Lens
struct Snapshot {
    let version: Int
    var isDraft: Bool
}

snapshot.throughLens.version.get()   // read the version
snapshot.throughLens.version.set(2)  // rebuilt snapshot with version 2
```

## Changing several fields

```swift
author.throughLens.changing(name: "narf")   // Person with name "narf"
author.throughLens.changing(
    name: "narf",
    address: Address(street: "Baker Street")
)
```

`changing` rebuilds the value through the memberwise initializer, so unlike
lenses it can replace stored `let` properties too — handy for settings and
other immutable value types. The same ability backs the bound lenses for
`let` properties described in "Bound lenses":

```swift
@Lens
struct Settings {
    let version: Int
    var isEnabled: Bool
}

settings.throughLens.changing(version: 2)
```

Passing `nil` (or omitting a parameter) keeps the current value; an optional
property cannot be set back to `nil` this way.

`changing` is not generated for structs with custom initializers or with
properties that have attributes/property wrappers — both suppress the
memberwise initializer it builds on — and such structs keep a plain
`throughLens`. Like the rest of the dot notation, `changing` is only
available on `throughLens` itself; once a chain focuses deeper
(`team.throughLens.lead`), the result is a plain bound lens.

## Behavior and limitations

- Only stored `var` properties with an explicit type annotation get an entry
  in the `Lenses` enum and chain through key paths; `let` properties get
  rebuild-based bound lenses on `throughLens` instead (whenever `changing`
  is available — see "Bound lenses").
- Computed properties, `static` members are skipped.
- Properties with attributes or property wrappers are skipped with a
  warning (wrappers can change what get/set mean, so the macro stays out of
  the way).
- `changing` is unavailable on structs with custom initializers or with
  properties that have attributes — they keep a plain `throughLens`.
- A property without an explicit type annotation gets a warning; add the
  annotation to get a lens for it.
- Attaching `@Lens` to anything other than a struct is an error.
- The generated members mirror the struct's access level (`public` structs
  get `public` lenses and a `public throughLens`).
- Generic structs get computed `static var` lenses instead of stored ones,
  because Swift does not allow static stored properties in generic types.

## Runtime API

| Member | Description |
| --- | --- |
| `Lens.get` | `(Whole) -> Part` reader |
| `Lens.set` | `(Part, Whole) -> Whole` writer returning a copy |
| `Lens.compose(_:)` | compose with a lens that focuses deeper |
| `Lens.identity` | the lens that focuses on the whole value itself |
| `Lens(_:)` | build an ad-hoc lens from a `WritableKeyPath` |
| `BoundLens.get()` | read the part of the bound instance |
| `BoundLens.set(_:)` | return the bound whole with the part replaced |
| `BoundLensType` | protocol for custom bound lens types |
| `throughLens` | generated on `@Lens` structs, starts a bound lens chain |
| `ThroughLens.changing(...)` | generated on `@Lens` structs, replaces several fields in one call |

## Requirements

- Swift 6.4+ toolchain (tested with Xcode 27) — macros need a matching
  swift-syntax, which SwiftPM fetches automatically.
- Platforms: macOS 10.15+, iOS 13+, tvOS 13+, watchOS 6+.

## Development

```sh
swift build        # build the library, macro implementation, and demo client
swift run LensClient
swift test         # runtime tests + macro expansion tests
```

Layout:

- `Sources/Lens` — runtime `Lens`/`BoundLens` types and the `@Lens` macro declaration
- `Sources/LensMacros` — macro implementation (`MemberMacro` + compiler plugin)
- `Sources/LensClient` — executable demo
- `Tests/LensTests` — end-to-end tests and `assertMacroExpansion` tests
